2The problem and the goal

Elasticsearch holds 1.28 GB of memory around the clock at almost no CPU: about $13 a month at Railway's $10 per GB. It searches 9 events and does nothing Postgres cannot: no text search, only a map radius or box, a time window, author and event filters, two sort orders and paging. record Railway metrics, 7 days; code at d9ab983; the $16 project total from the cost thread, Nov 16.

Goal: the same answers from query.iriai.app for about $13 a month less, with a measured trigger for bringing Elasticsearch back.

For Iriai (the bill) and every app calling query.iriai.app (they should notice nothing). We will know it worked when Railway's usage page shows Elasticsearch near $0, the acceptance check passes on Postgres, and the slowest 5% of searches stay under 250 ms.

3The experience

No screen changes. The actors are an app calling the API, you, and the controller in our ingester.

  1. An app searches. A 2 km search around Japantown returns the same events, in the same order and shape, from Postgres.
  2. The first page opens a paging session. The sealed cursor now also records which backend served it; apps cannot see this.
  3. Later pages see the same moment. An event edited after the first page shows its old version until the app searches again, exactly as today.
  4. Every day, the ingester checks two numbers. How slow the slowest 5% of searches were, and how many events exist. It reacts to slow searches on 3 days running with real traffic, or to 500,000 events.
  5. The trigger is met: Elasticsearch wakes. The controller calls Elasticsearch, which Railway wakes from sleep; it copies every event in, checks both give the same answers, and moves new searches over. You get a GitHub issue email.
  6. When use falls well below for 14 days, search moves back. New searches go to Postgres; Elasticsearch serves its open sessions for one more hour and is then turned off by the same route as step 5.
  7. Failure paths. If Elasticsearch fails to start or the answers differ, it is turned off again, nothing switches, and you get an issue; after 2 failures in 30 days the controller stops until someone clears it. While Elasticsearch serves, a first page it fails is answered from Postgres, and repeated failures move search back. A later page of a failing Elasticsearch session gets "service unavailable", as today. Near the trigger, a slow Postgres search can hit its 2 s limit and get "service unavailable". A cursor from a backend no longer serving gets CursorExpired, which tells the app to search again.

4How it works

One interface, two backends. The query service and the ingester talk to "a search backend" with seven calls. Postgres and Elasticsearch each implement them. planned Spec 3.

Postgres is always written and always complete. Every event lands in a new table, event_docs, whatever is serving, and single-event lookups always read it. Elasticsearch is written only while it is on, and a failed Elasticsearch write no longer holds up ingestion: a repair pass fixes it. planned Spec 5.

Elasticsearch becomes optional. Today both services refuse to start until Elasticsearch answers. PR 1 removes that wait, so turning Elasticsearch off cannot take the API down. code src/main.ts; spec 5.2.

More: same answers, paging, speed, the trigger, the controller

Same answers. Filters, sort orders and tie-breaks are copied rule by rule, and every existing search test runs on both. Distances differ by a few millimetres, because Elasticsearch rounds stored points to about 1 cm: two results within about 5 cm of each other's distance can swap, and an event within 5 cm of a radius edge can fall either side. planned Spec 4.4.

Paging. Every write gets a number. When an event changes, Postgres keeps its previous version for 61 minutes. A search's first page takes the latest number, after any write in flight finishes, and every page reads the versions as of that number. Sessions last at most an hour. D1. planned Spec 4.2, 4.3.

Speed, measured. On a scratch Postgres (4 vCPU, all in memory) every query shape took under 10 ms at 10,000 events and under 45 ms at 100,000. At a million, map searches took 14 to 70 ms, a week by start 65 to 79 ms, and a month by start or the default "everything by distance from here" about 290 to 345 ms. Railway will be slower. Today there are 9 events. code spike; spec 4.5.

The trigger. The query service writes daily stats: calls, the slowest-5% time per backend, the event count, and up to 200 query shapes (coordinates rounded to about 100 m) kept 7 days for the switch-over check. While Elasticsearch serves, 1 in 10 searches is also timed on Postgres after the answer is sent. D2. planned Spec 6.1, 6.2.

On and off. Railway's Serverless setting puts Elasticsearch to sleep 5 to 10 minutes after it last sent anything, and a request wakes it. "On" means the controller calls it until it answers, then checks it every 2 minutes so it stays awake; "off" means our services send it nothing. Our code holds no Railway credential, so a weekly check this thread sets up reads its memory on Railway to confirm it sleeps. D3. docs Railway Serverless; waking over the private network is checked in gate 2. Spec 6.3.

One rule: Postgres serves once the ingester has filled it and seen it give the same answers as Elasticsearch, and from then on it always may: every write reaches it first. Elasticsearch serves only while freshly filled with no write waiting for repair. A search goes to the chosen backend if it may serve, else to Postgres. Until that first check passes, Elasticsearch stays on and serves alone, as today. Spec 5.2.

The controller runs in the ingester every 10 minutes and walks the states in 4d. Before moving searches it checks that both backends hold the same events at the same versions and give the same first page for every stored query shape. A repair pass compares the two every day while Elasticsearch serves. planned Spec 6.4.

In words
  1. Apps send search requests to the query service.
  2. The query service reads from Postgres, or from Elasticsearch only while it is on.
  3. The ingester reads the Bluesky event stream and writes every event to Postgres, and to Elasticsearch only while it is on.
  4. The controller in the ingester opens GitHub issues, which GitHub emails to you. How it turns Elasticsearch on and off is D3.

5Scope fence

  • In: the shared interface, Postgres search with the same answers, Elasticsearch made optional at start-up, the switch-over, the daily stats, the controller, its repair pass and its GitHub issues, every search test run on both backends.
  • Out: text search (none exists; wanting it would be its own proposal); the interim heap cut (the cost thread owns it); a staging copy of the index.
  • Deferred: deleting the Elasticsearch service and disk for good. Reopens if the trigger has not fired in 12 months.
  • Cut first if effort runs over: the controller (PR 2). PR 1 alone saves the money.

9Risks

  • It is 2 weeks later and an app sees different results. A rule was copied wrong. Mitigation: every search test runs on both backends, including antimeridian, ties and radius edges.
  • It is a month later and a page skipped an edited event. The snapshot was not exact. Mitigation: numbered writes (spec 4.3) and a test with concurrent writes.
  • It is a month later and Elasticsearch never sleeps. It sends traffic of its own, so it keeps billing about $13. Our code cannot see that. Mitigation: gate 2 watches it sleep on Railway's metrics, and a weekly check this thread sets up opens an issue if it stays awake; then you pick B or C.
  • It is a year later and the switch fails when it finally runs. Something changed since it was tested. Mitigation: the failure path turns Elasticsearch off and leaves Postgres serving; the forced dry run in gate 3 can be repeated.

14Glossary
